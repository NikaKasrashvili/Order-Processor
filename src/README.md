# OrdersApp

კონსოლური აპლიკაცია, რომელიც ამუშავებს `orders.json` ფაილს: აჩვენებს ყველა შეკვეთას, ეძებს კონკრეტული მომხმარებლის შეკვეთებს და ითვლის სტატისტიკას დასრულებულ შეკვეთებზე.

## გაშვება

**მოთხოვნა:** .NET 10 SDK (შემოწმებულია `10.0.300`-ზე).

```bash
# აპლიკაცია (default-ად კითხულობს orders.json-ს, რომელიც build-ისას output-ში კოპირდება)
dotnet run --project src/OrdersApp

# სხვა JSON ფაილით
dotnet run --project src/OrdersApp -- path/to/orders.json

# ტესტები
dotnet test
```

მენიუ:

```
1. Show all orders
2. Search orders by customer
3. Show statistics
0. Exit
```

მოცემულ `orders.json`-ზე მოსალოდნელი სტატისტიკა:

```
Completed orders: 3
Total sales: 425.00
Average order value: 141.67
Most popular product: Keyboard, Mouse
```

არასწორი ან არარსებული ფაილის შემთხვევაში პროგრამა ბეჭდავს შეტყობინებას და სრულდება exit code `1`-ით (stack trace-ის გარეშე).

## გამოყენებული AI ინსტრუმენტები

- **Claude Code** (CLI) – კოდის, ტესტებისა და სპეციფიკაციის დაწერა. გამოვიყენე:
  - `CLAUDE.md` – პროექტის წესები (decimal ფულისთვის, მინიმალური არქიტექტურა, გეგმის შემუშავება კოდის წერის დაწყებამდე და ა.შ.);

  - `csharp-lsp` პლაგინი – რომ Claude-მა compile შეცდომები build-მდე დაინახოს;
  - საკუთარი **`spec-reviewer` subagent** – read-only რევიუერი (`Read`, `Grep`, `Glob` ხელსაწყოებით), რომელიც კოდს spec-თან ადარებს და კოდის წერის კონტექსტი არ აქვს.

## რაში დამეხმარა AI

- **ბუნდოვანი შემთხვევების ანალიზში.** Claude-მა დამოუკიდებლად იპოვა ყველა "მახე", რომელსაც წინასწარ ვვარაუდობდი:
  - **ფრე:** Keyboard (2+1) და Mouse (1+2) ორივე 3-ჯერაა გაყიდული. ტიპური `OrderByDescending(...).First()` მხოლოდ ერთს დააბრუნებდა, მონაცემების რიგის მიხედვით, და არა ორივეს.
  - **რაოდენობა თუ შემოსავალი:** შემოსავლით Monitor იგებს (200, Keyboard-ის 150-ისა და Mouse-ის 75-ის წინააღმდეგ). მონაცემები ისეა შერჩეული, რომ ორი მიდგომა სხვადასხვა პასუხს იძლევა, ამიტომ სწორად გაიაზრა მოთხოვნა, რომ რაოდენობის მიხედვით  დაეთვალა და არა ჯამური შემოსავლის.
  - **გაუქმებული შეკვეთა #2:** შეცდომით ჩათვლისას შედეგი 4 / 475 / 118.75 გამოვა 3 / 425 / 141.67-ის ნაცვლად.
  - **დამრგვალება:** 425 / 3 = 141.666…; `int`-ებით გაყოფა 141-ს მისცემდა, ხოლო C#-ის `Math.Round` default-ად banker's rounding-ს იყენებს.

  ერთი რამ უკეთ დაინახა: #2-ის ჩათვლისას Keyboard რაოდენობა 4 ხდება და შესაბამისად ეს შეცდომა ფრეს **მალავს**. ამიტომ ტესტები ფრეს და cancelled-ის გამორიცხვას ცალ-ცალკე ამოწმებს.
- **კოდისა და ტესტების წერა:** – გეგმის შედგენა, მოსალოდნელი შედეგების აღწერა და შესაბამისად კოდისა და ტესტების იმპლემენტაცია წინასწარ განსაზღვრული სტრუქტურის ფარგლებში.
- **Edge case, რომელიც გამომრჩა:** გეგმაში Claude-მა თავად შენიშნა, რომ positional record-ში JSON-ში გამოტოვებული `items` `null` გახდებოდა და არა ცარიელი სია, და შესაბამისი გამოსწორების გზაც იპოვა.

## AI-ის შეცდომები და როგორ გამოვასწორე
 
1. **ბაგი, რომელიც ტესტებმა ვერ დაიჭირა.** სტატისტიკის ფუნქციის იმპლემენტაციისას, ყველა ტესტი მწვანე იყო. spec ფაილში აღწერილია, რომ შეკვეთა ცარიელი `items`-ით ვალიდურია.
   ფუნქციის დასაწყისში იყო შემოწმება "თუ დასრულებული შეკვეთა არ არის, დააბრუნე ნულები", ასე რომ ცარიელ სიაზე პრობლემა არ იყო. მაგრამ AI-მ ივარაუდა, რომ თუ დასრულებული შეკვეთა არსებობს, მასში პროდუქტებიც იქნება. ასეთ შემთხვევაში შეკვეთა შემოწმებას გაივლის, პროდუქტების სია ცარიელია და ყველაზე პოპულარულის საპოვნელად `Max()` ცარიელ სიაზე გამოიძახება. `Sum()` ცარიელ სიაზე 0-ს აბრუნებს, `Max()` კი exception-ს აგდებს, რადგან "არაფრის მაქსიმუმი" არ არსებობს.
   ტესტები ამას ვერ იჭერდა, რადგან ყველა ან ჩვეულებრივ მონაცემებს ამოწმებდა, ან შემთხვევას, როცა შეკვეთები საერთოდ არ არის. "შეკვეთა არის, პროდუქტი არა" არცერთში არ იყო.
   ჯერ ტესტი დავწერე ზუსტად ამ შემთხვევისთვის და დავრწმუნდი, რომ ის ჩავარდა, რათა დავრწმუნებულიყავი რომ ბაგი რეალურია, შემდეგ  კი გავასწორე: ცარიელ სიაზე მაქსიმუმი 0 გახდა (`DefaultIfEmpty(0)`) და ტესტი გავიდა.
2. **ტესტები spec-ის ორ წესს არ ამოწმებდა.** როცა AI-მ ტესტები დაწერა, ჯერ მოსალოდნელი რიცხვები გადავამოწმე (3, 425, 141.67, Keyboard და Mouse), ყველა სწორი იყო, თუმცა ორი შემთხვევა არ იყო გათვალისწინებული.
   პირველი - spec ამბობს: სტატისტიკაში ითვლება მხოლოდ `completed`, ყველა სხვა სტატუსი გამოირიცხება. ტესტებში კი მხოლოდ `completed` და `cancelled` იყო. ეს ნიშნავს, რომ თუ იმპლემენტაციის ლოგიკა ისე აიგებოდა, რომ "ყველაფერი, გარდა `cancelled`-ისა", ყველა ტესტი გაივლიდა, თუმცა `pending` შეკვეთა სტატისტიკაში მოხვდებოდა. ამიტომ ტესტში `pending` შეკვეთის შემთხვევაც დავამატე.
   მეორე - ცარიელი სახელით ძებნა, რომელიც spec-ის მიხედვით ცარიელ შედეგს აბრუნებს. ორივე ტესტი იმპლემენტაციამდე დავამატე.
3. **ტესტი, რომელიც თითქოს ამოწმებდა, მაგრამ სინამდვილეში არა.** საშუალოს ტესტი ასე იყო დაწერილი: `Assert.Equal(141.67m, avg, 2)`. ერთი შეხედვით სწორია, მაგრამ ეს `2` ორივე რიცხვს შედარებამდე ამრგვალებს. ანუ ტესტი გაივლიდა მაშინაც, თუ სერვისი ზუსტ `141.666…`-ს დააბრუნებდა და მაშინაც, თუ უკვე დამრგვალებულ `141.67`-ს. spec-ის წესს ("სერვისში არ მრგვალდება") ის ვერ იცავდა. ეს რევიუერმა იპოვა. შევცვალე ზუსტი შედარებით: `Assert.Equal(425m / 3m, avg)`.
4. **რევიუერმა არასწორი რჩევა მომცა.** რევიუერმა შემომთავაზა `Order` record-ის გამარტივება: `Items`-ის ცალკე property-ს ნაცვლად default მნიშვნელობა პირდაპირ constructor-ში (IReadOnlyList<OrderItem> Items = []). ეს მცდარია, რადგან `[]` constructor-ის default-ად ვერ დაიწერება (compile-time constant არ არის), ხოლო `null` default-ით ზუსტად ის პრობლემა ბრუნდება, რომლის გამოც ეს კოდი დაიწერა: System.Text.Json JSON-ში გამოტოვებულ `items`-ს `null`-ად გადასცემს და არა ცარიელ სიად. 


### დამოუკიდებელი რევიუ
 
კოდის შემოწმების  მიზნით, შევქმენი ე.წ. `spec-reviewer` აგენტი (`.claude/agents/`), რომელსაც მხოლოდ ფაილების კითხვა შეუძლია და შეცვლა არა. შემდეგ, ახალ სესიაში აგენტს დავავალე კოდის შემოწმება: იმპლემენტაციის შესაბამისობა spec ფაილთან.
 
 რევიუმ 9 შენიშვნა მოიტანა, სერიოზული არცერთი. საბოლოოდ, აღნიშნული შენიშვნებიდან:
 
- **სამი მივიღე.** loader-ს ტესტები საერთოდ არ ჰქონდა. ეს ყველაზე მნიშვნელოვანი იყო, რადგან წესი "`items`-ის გარეშე შეკვეთა = ცარიელი სია" მანამდე მხოლოდ ხელით მქონდა შემოწმებული. დავამატე 3 ტესტი. ასევე სუსტი assertion საშუალოზე (იხ. პუნქტი 3) და ცარიელ სიაზე მენიუს ოფცია 1, რომელიც არაფერს ბეჭდავდა.
- **ოთხი უარვყავი.** პროდუქტების სორტირება მხოლოდ case-sensitive-ია და null `status`/`customer`-ზე პროგრამა ვარდება, მაგრამ ორივე spec-ში შეგნებულად out of scope-ია: შემავალ მონაცემებს ვენდობით. `Items`-ის "გამარტივება" ტექნიკურად მცდარი იყო (პუნქტი 4). `TextReader`/`TextWriter` და `OrderLoadException` "ზედმეტად" მონიშნა, მაგრამ ორივე პატარა და გამართლებულია: პირველი მენიუს ტესტირებადობისთვისაა, მეორე კი მოსალოდნელ შეცდომას (ცუდი ფაილი) ბაგისგან განასხვავებს.
- **ორი გამოვტოვე.** ცალკეული შეკვეთის ჯამის პირდაპირი ტესტი და სახელის whitespace შენახულ მონაცემებში. ორივე ირიბად დაფარულია ან ძალიან დაბალი რისკისაა.

გასწორებების შემდეგ აგენტი ხელახლა გავუშვი: spec-თან შეუსაბამობა ან სერიოზული პრობლემა აღარ აღმოჩნდა. ერთი შენიშვნა შეგნებულად დავტოვე: ეკრანზე ჩვენებისას დამრგვალება (`AwayFromZero`) ავტომატურად არ იტესტება, მხოლოდ ხელით შევამოწმე.
